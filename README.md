## What counts as harness self-evolution

A **harness** is the executable system between a model and a task: it loads instructions and context, routes memory and skills, schedules workflow steps, calls tools, enforces permissions, and runs verification or replay hooks. Write $H_s$ for that execution under versioned model-external state $s$, so a task $z$ produces $\tau = H_s(M, z)$.

An entry is listed when all three conditions hold:

1. **the base model is fixed** for the update under discussion;
2. **run-time evidence** influences a change to an explicitly delimited state set $\mathcal S_{\mathrm{edit}}$; and
3. **the changed state is reloaded by later runs**, with an explicit accept/reject rule when one exists.

Temporary context, processes, caches, and generated files belong to the run, not to $s$, unless they are versioned and reloaded. Tasks, evaluators, model routing, permissions, and logging are protected boundary components by default: a candidate that can change them is an evaluation-boundary change, not an ordinary harness edit.

In scope: prompt optimization, self-evolving memory and skills, workflow search, self-modifying harness code, and optimizer/meta-harness code. Methods that update harness and weights together are boundary cases and are marked. Weight-only training and hand-authored harness design appear only where they clarify the boundary.

## How to read this list

Each entry records three fields that describe *different parts of one update loop*. None is a synonym for another.

| Field | Question it answers | Values |
|---|---|---|
| **Editable surface** | What persistent object can change? | `L0`–`L5`, below |
| **Proposal mechanism** | Who forms the candidate, and from what evidence? | `proposer`, `search`, `co-learning`, `runtime policy`, `self-modifier` |
| **Confirmation protocol** | What rule decides that a candidate becomes the next state, and what data can affect that rule? | `write-through`, `selection`, `separated` |

The level is an **object range, not a capability score**. A higher level is not a better system.

| Level | Editable object | Typical edit unit |
|---|---|---|
| **L0** | instruction prompt | prompt, instruction block, exemplar |
| **L1** | context, memory, skill | entry, file, retrieval unit, executable skill |
| **L2** | workflow, graph, architecture | node, edge, subgraph, module slot |
| **L3** | harness or agent code | file, module, tool, plugin |
| **L4** | improver, optimizer, context mechanism | proposer, selector, search operator |
| **L5** | harness *and* model adaptation | checkpoint, LoRA, prefix plus harness state |

Marks: `†` boundary entry (joint model–harness, runtime-only, or self-modifying) · `‡` adjacent program-evolution sample · `ᴮ` coverage entry outside the counted snapshot · `—` deliberately unfilled.

`ᴮ` is a statement about the **counts**, not about the paper. The snapshot is frozen while the companion survey is drafted, so a recent entry stays outside it even when its fields have been checked; those carry an `audit` link to [docs/audit-table.md](docs/audit-table.md).

> The scarcity of ✅ is the point of this list. Proposal mechanisms are common; candidate-level independent confirmation is not. A protocol field is only filled when a primary source establishes it — never inferred from a system's level, benchmark, or use of the word "validation".
<!-- END:STATS -->

Why proposal and confirmation are recorded separately: an improvement observed on the same tasks that produced the candidate supports a ranking, not a guarantee about fresh tasks. Only `separated` admits fixed-candidate holdout reasoning, and only under stated independence, bounded-loss, and protected-boundary assumptions — see [docs/pac-stability.md](docs/pac-stability.md). Human review, sandboxing, audit logs, and rollback are governance controls; they do not create statistical independence. A hook that never executes is equivalent to no gate.

For the proposal side, [docs/zo-operator-map.md](docs/zo-operator-map.md) maps each mechanism to its zeroth-order analogue and states where the analogy stops: a textual critique is not a numerical gradient, a parent/child pair is not a central difference, and a rejected-candidate buffer is not a control variate.

## Benchmarks and evaluation substrates

None of these supplies a self-evolution protocol on its own. Episodic benchmarks do not measure persistent state, and scores across different base models, harnesses, optimizers, and evaluators are not directly additive. The correct unit of evaluation is an **evolution trajectory**, not a final-version score — see [docs/evaluation-protocol.md](docs/evaluation-protocol.md) for the reporting schema.

**Task substrates**

- [SWE-bench](https://arxiv.org/abs/2310.06770) — repository-level issue resolution; the standard coding target.
- [MLE-bench](https://arxiv.org/abs/2410.07095) — 75 Kaggle-style machine-learning engineering tasks.
- [RE-Bench](https://arxiv.org/abs/2411.15114) — ML R&D tasks benchmarked against human experts.
- [PaperBench](https://arxiv.org/abs/2504.01848) — reproduction of 20 ICML papers from scratch.
- [Terminal-Bench](https://openreview.net/forum?id=a7Qa4CcHak) — terminal-native long-horizon tasks.

**Harness and environment substrates**

- [SWE-agent](https://arxiv.org/abs/2405.15793) — agent–computer interface design for repository tasks.
- [OpenHands](https://arxiv.org/abs/2407.16741) · [OpenHands SDK](https://arxiv.org/abs/2511.03690) — open agent platform and its programmable harness layer.
- [BrowserGym ecosystem](https://arxiv.org/abs/2412.05467) — unified web-agent environments and evaluation.
- [ToolSandbox](https://arxiv.org/abs/2408.04682) — stateful, conversational tool-use evaluation.
- [$\tau$-bench](https://arxiv.org/abs/2406.12045) — tool–agent–user interaction under domain policies.
- [AgentDojo](https://arxiv.org/abs/2406.13352) — adversarial prompt-injection evaluation for tool-calling agents.
- [WorkArena](https://arxiv.org/abs/2403.07718) — enterprise knowledge-work tasks over a real web platform.

**Measurement integrity**

- [AI Agents That Matter](https://arxiv.org/abs/2407.01502) — accuracy-only leaderboards hide cost and holdout discipline.
- [HAL](https://arxiv.org/abs/2510.11977) — cost-aware third-party agent leaderboard.

**Failure modes that motivate a gate**

- [Misevolution](https://arxiv.org/abs/2509.26354) — emergent risks specific to self-evolving agents.
- [Defining and Characterizing Reward Hacking](https://arxiv.org/abs/2209.13085) · [Scaling Laws for Reward Model Overoptimization](https://arxiv.org/abs/2210.10760) · [Sycophancy to Subterfuge](https://arxiv.org/abs/2406.10162) — why an improving proxy score is not an improving system.

## Contributing

The catalogue is **generated**, so a pull request edits data rather than markup. See [CONTRIBUTING.md](CONTRIBUTING.md) for the full rules; the short version:

| Change | Where | Review |
|---|---|---|
| Add or fix a title, venue, code link, or one-line summary | [`data/paper-meta.md`](data/paper-meta.md) | merged on verification |
| Add a paper | open an issue; it enters as a coverage entry (`ᴮ`), outside the counted snapshot | low bar |
| Assign or change an editable surface, proposal mechanism, or **confirmation protocol** | not accepted as a pull request | requires a primary-source audit upstream |

The last row is deliberate. A protocol field is only filled when a primary source establishes it. Please do not infer one from a system's level, its benchmark scores, or the paper's use of the word "validation" — an unfilled field is the correct answer when the source does not say.

Regenerate after a data change:

```bash
python3 scripts/build_readme.py
python3 scripts/check_consistency.py
```
